# incan.pub v0: a repository-based registry

v0 is the smallest incan.pub that lets Oven consume crates.io packages as Loaves, without Cargo, and lets the toolchain pin what it consumed. It is a repository, not a service: the registry's data is a git branch, its admission is a program anyone can run, and source Loaf archives sit in a blob store addressed by digest. Hosting, a CDN, signed checkpoints and baked-asset distribution come later and change how the same files arrive, not what they say. This page defines v0; [model.md](model.md) states the loop it implements and [RFC 125](https://github.com/encero-systems/incan/blob/main/workspaces/docs-site/docs/RFCs/125_incan_pub_loaf_registry_and_baked_asset_distribution.md) the destination.

## Shape

```
encero-systems/incan.pub
├── main    the tool (incan-pub, written in Incan), the docs, the explanation page
└── index   the data: events/, index/, crates-io/**/loaf.toml (+ out/)   ← what the toolchain reads and pins

blob store  sha256/<hex>.tar   source Loaf archives, outside git
```

Two branches of one repository, as a docsite is a branch of the project it documents and as `crates.io-index` sits beside `crates.io`. `main` changes when the tool or its rules change; `index` changes when something is adopted or published. A commit on `index` is the signed event and its `HEAD` the checkpoint. Nothing on `index` is authored except `events/`: the rendered manifests and the index are projections the tool regenerates, and CI refuses a push on which they disagree with the log.

## The programs

| program | where it runs | what it does |
|---|---|---|
| **incan-pub** (this repository, `main`) | maintainers and CI | admission (`check`), projection (`build`), adoption (`adopt`, `readopt`), build facts (`record-fact`, which compiles and runs a build script sandboxed under one binding), the publishing verbs (`publish`, `add-fact`, `admit-drop`, `attest`, `advise`), and the registry verbs (`push-source`, `fetch-sources`, `pack-units`, `push-units`, `admit-assets`) |
| **the provider** (the Incan toolchain) | inside the toolchain | opens a checkout of `index` at a pinned commit, resolves from the index lines, and selects the fact bound to its own exact selection, refusing otherwise; never writes into the checkout |
| **the harvest** (the Incan toolchain) | a maintainer's machine, once per exact selection | emits a [proposal](harvest-proposal.md) for `incan-pub add-fact` or `admit-drop` |

## What is in the data branch

- `events/NNNNNN-<kind>-<subject>.json` — the append-only log. `publish`, `adopt`, `fact`, `attest`, `asset`, `yank`, `unyank`, `advisory`; each event carries `schema`, `kind`, `at`, `actor`, `subject` and an `id` that is the SHA-256 of its canonical body (sorted keys, no whitespace, JSON escaping only where JSON requires it, UTF-8). `signature` is `null` and reserved for the signed form. Sequence numbers are contiguous; a tampered or reordered file fails admission before any rule is applied.
- `index/crates-io/<name>` — projection: one canonical-JSON line per version, enough to resolve the whole graph before any archive is fetched. An adopted version carries `name` (`crates-io/<name>`), `vers`, `cksum` (the source Loaf archive digest), `facets`, `rust` (`name`, `type`, `edition`), `deps` (one element per declaration: `name`, `loaf`, `req`, `features`, `default-features`, `optional`, and `target` when conditional), `features`, `adopted` (`registry`, `package`, `version`, `checksum`), `publisher`, `manifest`, `yanked`, `facts[]` with a `status` of `harvested` or `attested` per binding, and `owners` on a fact whose `link` or `tool` executables need them present, and the `assets` and `advisories` counts.
- `crates-io/<name>/<version>/loaf.toml` — projection: the adopted manifest followed by its bound facts ([external-source-record.md](external-source-record.md) for the facts).
- `crates-io/<name>/<version>/assets.json` — projection, present once a version has assets: the asset manifest. Each asset carries its `binding`, `archive` digest, `unit_identity`, store `entry` identity, `payload` digest, `builder`, `attestation`, and `location` (`registry`, `repository`, `tag`). Assets are ordered by binding, then unit.
- `crates-io/<name>/README.md` — projection: the package page, every version newest first.
- `catalog/index.json` — projection: the catalog a site or tool lists packages from. It carries `schema` (`incan.pub/catalog/1`), `log` (the number of `events` and the `id` and `at` of the `last` one; a file cannot name the commit that holds it), `counts` (`packages`, `versions`, `facts`, `assets`) and `packages[]`, sorted by name: each with its scoped `name`, the `latest` adopted version that is not yanked, the number of adopted `versions`, that version's `description` and `license`, the `build-targets` it has compiled units for, and its `page`.
- `catalog/crates-io/<name>.json` — projection: a package's catalog page, `schema` `incan.pub/catalog-package/1`, its scoped `name`, its `upstream` (`registry`, `package`, `url`) and every adopted version newest first: `version`, `yanked`, `adopted` (the time of adoption, not of the upstream release), `registry` (`adopter`, `publisher`; the package's own `authors` are in `about`), `manifest`, `archive` (the source Loaf archive digest), `upstream` (`registry`, `package`, `version` and the upstream `checksum` it was adopted from), `rust`, `features` and `dependencies` (the index line's `features` and `deps`: each declaration's `name` as the manifest spells it, its `loaf`, `req`, `features`, `default-features`, `optional` and `target` when conditional), `about`, `keywords` and `categories` (exactly as the manifest declares them; empty when it declares none), `vcs` (the git `commit`, the package's `path` in the repository and `dirty` as `cargo package` recorded them, or `null` when it recorded none), `files` (whether the `readme` and `license` come from the `package` archive or were generated by the `registry`), `documents` (the README, license texts or the registry's `license-notice`, and changelogs: each `role`, `path` in the archive, `digest`, `bytes`, `format`, `origin` and the `content` path holding its bytes), `facts` (each binding: `toolchain`, `target`, `profile`, `features`, with its `status` and `owners`), `assets` and the `advisories` count.
- `content/sha256/<hex>` — the bytes of each document an adoption names, by digest: what a catalog `content` path points to. `check` refuses one no adoption names, and admission one whose bytes are not its digest. The branch's `.gitattributes` (`* -text`) keeps git from converting line endings, so a checkout holds the bytes the digests name.
- `crates-io/<name>/<version>/out/…` — the committed generated inputs a fact names, each bound by digest.
- `graphs/<hex>.json` — the resolutions bound facts were selected from, committed once and named by digest from a fact's `evidence.graph`, with the unit's `evidence.domain` beside it ([harvest-proposal.md](harvest-proposal.md)). Older facts name none.

## Adoption

`incan-pub adopt` turns crates.io package versions into Loaves under RFC 125's fixed rules. For each version it fetches the crates.io index line and the `.crate` archive into a cache, verifies the archive against the crates.io checksum before reading it, reads only the edition and the library target from the archive's manifest, and translates the rest from the index line: normal dependencies kept one per declaration under their extern name, development and build dependencies and `links` dropped, implicit optional features made explicit, `x/f` on an optional `x` rewritten so the enabled feature set is unchanged, and every target normalized to a canonical `cfg(...)` or kept as an exact triple. The manifest and the package's files form the source Loaf archive, a deterministic uncompressed tar (entries sorted by path, mode 0644 or 0755, mtime and owners zeroed), written to the blob store under its digest.

Admission refuses an `adopt` event unless every dependency active under the version's default features, on any target, is met by a version already adopted: every non-optional declaration, target-conditional ones included, and every optional one the default features enable. A dependency only a further feature enables need not be on the pin; a remote provider answers it "not published" and the local store adopts it on demand. `adopt` therefore plans that closure first: a requirement no adopted version meets is met by the newest crates.io version satisfying it, preferring one that is not yanked. The events are then appended in dependency order.

## Admission, in one place

`incan-pub check` on a checkout of `index`:

1. reads the log in sequence, refusing gaps, unknown kinds, a kind that differs from the file name, a missing schema, actor or timestamp, and an `id` that is not the digest of the body;
2. folds it under the rules: a version publishes or is adopted once, and an identical repeated adoption is a no-op while a different one is refused; an adoption's `manifest` digest must be the digest of the manifest its own payload renders, and every dependency active under its default features must already be adopted; a record must exist before anything else is said about it; a fact's binding is the four keys and nothing else, `cfg` and `features` sorted and unique, every `out` file present under the record with the digest it names, `harvested-from` a `sha256:` receipt; a repeated binding must repeat its facts exactly, except that a fact with `link` or `tool` records is keyed by its binding and its executables' owner identities, so one binding holds one such fact per compiler owner; a fact's `evidence.domain` and `evidence.graph` come together or not at all, and the graph is committed in its canonical spelling; an attestation names a bound fact and carries `sha256:` identities; an asset carries `sha256:` identities and a registry location and belongs to an adopted record, and one unit identity names one archive; a builder is `publisher`, `registry` or `local`;
3. renders the projections and compares them byte for byte with the committed ones, and refuses committed generated inputs and graphs no fact names;
4. given `--crates-io-index DIR`, confirms every record's checksum is the one crates.io publishes for that version;
5. given `--blobs DIR`, confirms every adopted version's source Loaf archive is in the blob store with the digest its index line names.

`check` opens no socket. Step 4 reads a snapshot of the crates.io sparse-index files that CI fetches with [scripts/snapshot-crates-io-index.sh](../scripts/snapshot-crates-io-index.sh) after asking the tool which packages the log names (`incan-pub index-urls`). `adopt` is the one verb that downloads, through the host's `curl`, and it verifies everything it downloads before reading it.

## What the toolchain needs from v0 and gets

- **Resolution from index lines.** Every adopted version's line carries its Rust facet, dependencies and features, so the whole graph resolves before any archive is fetched, and every pin is closed under dependencies.
- **Exact bindings.** A fact holds under one toolchain, target, profile and complete feature set. The provider matches its own selection exactly and refuses to interpolate. This is what lets Oven compile an adopted package without running its build script and still be right.
- **Committed generated inputs.** What a build script would have written to `OUT_DIR` is a file in the record, named and bound by digest. The provider reads it; nothing executes.
- **A pinnable checkpoint.** A commit. The toolchain pins it; a consumer with the same pin resolves the same records.
- **Status per binding.** `harvested` until an Oven-baked unit is proven equivalent, then `attested`. A consumer may refuse `harvested` bindings by policy.

## Learned from PyPI and crates.io

- **The index is derived, never authored** (crates.io: the index repository is written only by the service; PyPI: PEP 503/691 pages are generated from the database). Here the events are the database and the tool writes the index. A hand edit fails `check`.
- **Sparse layout over a git clone** (crates.io RFC 2789). A client fetches the one file it needs. v0 clones because it is small; the same layout serves over HTTPS unchanged when that time comes.
- **Immutability and yank** (both). A published or adopted version is never changed or removed; `yank` is an event that shows on the index line, so a consumer with a lock still resolves.
- **Content identity, not location** (crates.io `cksum`; PyPI hashes in file URLs). An adopted Loaf is its archive digest, with provenance back to the crates.io checksum it was adopted from.
- **Attestations as published facts, not gatekeeping** (PEP 740; crates.io trusted publishing). `attest` records evidence a client can demand; the registry does not judge truth.
- **Overlay declarations for third-party build behavior** (Meta's reindeer fixups; Bazel `crate_universe` annotations). The closest analog to a bound fact: a per-crate declaration of what a build script would have done. v0 makes that declaration a published, bound, immutable fact instead of a per-repository patch.

## Not in v0

- No hosting, CDN, or HTTPS transport; no signed index or periodic checkpoint. A commit is the signature.
- No baked-asset distribution. `asset` events are admitted so the vocabulary is complete, and source Loaf archives are written to the blob store, but nothing serves either yet.
- No third-party publishers, scopes or ownership. The `crates-io` scope is operated by the toolchain's maintainers, and an event's `actor` is a recorded name, not a verified identity.
- No mirror of crates.io. Only versions Incan users need are adopted.

## The one rule about the tool

It is written in Incan, with nothing but the standard library and Rust's own `std` for the argument vector and for running `curl`. A registry whose admission were written in another language would be a claim the language cannot make about itself.

## The toolchain it is built with

The Incan dev line. No release installs it yet, so CI builds the compiler at the commit `.github/workflows/check.yml` pins, in one place. A compiler gap the tool meets is worked around in place, with a comment naming it, and reported to the dev line.
