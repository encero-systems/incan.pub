# incan.pub v0: a repository-based registry

v0 is the smallest incan.pub that lets Oven bake adopted crates.io packages natively and lets 0.6 pin what it consumed. It is a repository, not a service: the registry's data is a git branch, its admission is a program anyone can run, and the toolchain's provider is a read-only overlay of a pinned checkout over the local Oven store. Hosting, a CDN, signed checkpoints and baked-asset distribution come later and change how the same files arrive, not what they say. This page defines v0; [model.md](model.md) states the loop it implements and [RFC 125](https://github.com/encero-systems/incan/blob/main/workspaces/docs-site/docs/RFCs/125_incan_pub_loaf_registry_and_baked_asset_distribution.md) the destination.

## Shape

```
encero-systems/incan.pub
├── main    the tool (incan-pub, written in Incan), the docs, the explanation page
└── index   the data: events/, crates-io/**/loaf.toml (+ out/), index/   ← what the toolchain reads and pins
```

Two branches of one repository, as a docsite is a branch of the project it documents and as `crates.io-index` sits beside `crates.io`. `main` changes when the tool or its rules change; `index` changes when something is published. A commit on `index` is the signed event and its `HEAD` the checkpoint. Nothing on `index` is authored except `events/`: the rendered records and the sparse index are projections the tool regenerates, and CI refuses a push on which they disagree with the log.

## The three programs

| program | where it runs | what it does |
|---|---|---|
| **incan-pub** (this repository, `main`) | maintainers and CI | admission (`check`), projection (`build`), the publishing verbs (`publish`, `add-fact`, `attest`) |
| **the provider** (incan 0.6, `oven_model::loaf_registry`) | inside the toolchain | opens a checkout of `index` at a pinned commit, reads the index line for a package, verifies the checksum it names, reads the rendered record, selects the fact bound to its own exact selection, refuses otherwise; never writes into the checkout |
| **oven harvest** (incan 0.6) | a maintainer's machine, once per exact selection | runs the compatibility publisher and emits a [proposal](harvest-proposal.md) for `incan-pub add-fact` |

The provider is an RFC 117 registered source whose kind is "git checkout at a revision". A user installs nothing beyond incan: the toolchain manifest pins the `index` commit, `oven.lock` records for each unit which record satisfied it, and the checkout lives under the Oven store like any other fetched source. Baked units land in the local Oven store through the same path a local bake uses; the checkout is a metadata layer over that store, never a second store.

## What is in the data branch

- `events/NNNNNN-<kind>-<subject>.json` — the append-only log. `publish`, `fact`, `attest`, `asset`, `yank`, `unyank`, `advisory`; each event carries `schema`, `kind`, `at`, `actor`, `subject` and an `id` that is the SHA-256 of its canonical body (sorted keys, no whitespace, JSON escaping only where JSON requires it, UTF-8). `signature` is `null` and reserved for the signed form. Sequence numbers are contiguous; a tampered or reordered file fails admission before any rule is applied.
- `crates-io/<name>/<version>/loaf.toml` — projection: the external-source record as a consumer reads it ([external-source-record.md](external-source-record.md)).
- `crates-io/<name>/<version>/out/…` — the committed generated inputs a fact record names, each bound by digest.
- `index/<sparse path>` — projection: one canonical-JSON line per package version, laid out by the crates.io sparse-index scheme (`1/a`, `2/ab`, `3/a/abc`, `se/rd/serde_core`): `name`, `vers`, `cksum`, `source`, `adopter`, `manifest`, `yanked`, `facts[]` with a `status` of `harvested` or `attested` per binding, `assets` (a count).

## Admission, in one place

`incan-pub check` on a checkout of `index`:

1. reads the log in sequence, refusing gaps, unknown kinds, a kind that differs from the file name, a missing schema, actor or timestamp, and an `id` that is not the digest of the body;
2. folds it under the rules: a version publishes once; a record must exist before anything else is said about it; a fact's binding is the four keys and nothing else, `cfg` and `features` sorted and unique, every `out` file present under the record with the digest it names, `harvested-from` a `sha256:` receipt; a repeated binding must repeat `cfg` and `out` exactly; an attestation or asset names a bound fact and carries `sha256:` identities; a builder is `publisher`, `registry` or `local`;
3. renders the projections and compares them byte for byte with the committed ones;
4. given `--crates-io-index DIR`, confirms every record's checksum is the one crates.io publishes for that version.

The tool opens no socket. Step 4 reads a snapshot of the crates.io sparse-index files that CI fetches with [scripts/snapshot-crates-io-index.sh](../scripts/snapshot-crates-io-index.sh) after asking the tool which packages the log names (`incan-pub index-urls`). A check therefore runs identically offline and in CI, and the network is a CI concern rather than a property of admission.

## What 0.6 needs from v0 and gets

- **Exact bindings.** A fact holds under one toolchain, target, profile and complete feature set. The provider matches its own selection exactly and refuses to interpolate. This is what lets Oven compile an adopted crate without running its build script and still be right.
- **Committed generated inputs.** What a build script would have written to `OUT_DIR` is a file in the record, named and bound by digest. The provider reads it; nothing executes.
- **A pinnable checkpoint.** A commit. The toolchain manifest pins it; a consumer with the same pin resolves the same records.
- **Status per binding.** `harvested` until an Oven-baked unit is proven equivalent to the Cargo-built one, then `attested`. A consumer may refuse `harvested` bindings by policy. This is where "Oven is real" becomes a property one checks per crate rather than asserts.
- **A cross-check while both paths coexist.** The compiler compares declared facts to what the compatibility publisher observes and refuses on disagreement (`LoafRegistryAuthority`), so a wrong record is caught by the first consumer, not the last.

## Learned from PyPI and crates.io

- **The index is derived, never authored** (crates.io: the index repository is written only by the service; PyPI: PEP 503/691 pages are generated from the database). Here the events are the database and the tool writes the index. A hand edit fails `check`.
- **Sparse layout over a git clone** (crates.io RFC 2789). A client fetches the one file it needs. v0 clones because it is small; the same layout serves over HTTPS unchanged when that time comes.
- **Immutability and yank** (both). A published version is never changed or removed; `yank` is an event that shows on the index line, so a consumer with a lock still resolves.
- **Content identity, not location** (crates.io `cksum`; PyPI hashes in file URLs). A record binds to a crates.io archive by SHA-256, and the registry never mirrors the archive.
- **Attestations as published facts, not gatekeeping** (PEP 740; crates.io trusted publishing). `attest` records evidence a client can demand; the registry does not judge truth.
- **Overlay declarations for third-party build behavior** (Meta's reindeer fixups; Bazel `crate_universe` annotations). The closest analog to an external-source record: a per-crate declaration of what a build script would have done, maintained beside the consumer rather than upstream. v0 makes that declaration a published, bound, immutable fact instead of a per-repository patch.

## Not in v0

- No hosting, CDN, or HTTPS transport; no signed index or periodic checkpoint. A commit is the signature.
- No source Loaf publication and no baked-asset distribution. `asset` events are admitted so the vocabulary is complete, but nothing serves an archive.
- No third-party publishers, scopes or ownership. The `crates-io` scope is operated by the toolchain's maintainers, and an event's `actor` is a recorded name, not a verified identity.
- No mirror of crates.io. Verification reads crates.io's own index lines; source archives are fetched from crates.io as before.

## The one rule about the tool

It is written in Incan and built by the released toolchain, with nothing but the standard library and Rust's own `std` for the argument vector and UTF-8 bytes. A registry whose admission were written in another language would be a claim the language cannot make about itself.
